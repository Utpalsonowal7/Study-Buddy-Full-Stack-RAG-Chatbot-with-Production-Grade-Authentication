# Backend deployment

The repository provides a Docker image for hosting services or a VPS. Deployment needs a hosting account, PostgreSQL with TLS and pgvector, Redis, and real provider credentials. Building the image does not publish the backend.

## Deploy on Render

1. In [Render](https://dashboard.render.com/), choose **New → Blueprint** and connect this GitHub repository on `main`.
2. Render reads `render.yaml` and prepares one Docker web service on the free plan. This blueprint does not provision a database or Redis; use existing TLS-enabled PostgreSQL/pgvector and Redis services. Review current Render plan limits before launching.
3. Fill the prompted variables securely in Render. Use the exact `CLOUDNARY_*` spelling the code reads. JWT signing secrets are generated by the blueprint. Set the frontend URL with a trailing slash for the existing OAuth redirect code.
4. Launch the blueprint and inspect build/startup logs. Once healthy, Render supplies the public HTTPS service URL. Use that URL plus `/api/v1` as your frontend API base.
5. Configure your frontend's actual origin in CORS before rollout. For authentication across unrelated sites (for example a Vercel frontend and an onrender.com API), the current SameSite=Lax cookies need adjustment and appropriate CSRF protection, or use same-site custom domains. Do not assume login cookies will work across unrelated domains without that change.

GitHub OAuth fields default to empty strings so the backend can import without GitHub configured; replace them and add the other provider variables when enabling OAuth. Free hosting can sleep and has resource limits; it is suitable for evaluating a demo, not evidence of production availability.

## Container details

- Build from the repository root with `docker build -t study-buddy .`.
- The image installs locked dependencies on Python 3.14 and runs Uvicorn as a non-root user.
- Supply configuration through your host's environment/secret settings. `.env` files are excluded from the image.
- Set `PORT` if your platform requires it; default is 8000. Bind to that container port.
- Configure the health check path as `/api/v1/health` (200 means PostgreSQL and Redis are reachable).
- Use the variable names and OAuth configuration in [README.md](README.md). Set `COOKIE_SECURE=true`, stable independent JWT signing secrets, and your deployed `FRONTEND_URL`.
- PostgreSQL needs pgvector installed and enabled before startup, or a role permitted to enable it. The app requires TLS. Set `DATABASE_URL` with the `postgresql+asyncpg://` scheme. Redis uses `redis://` or `rediss://` rather than a REST URL.
- Add your frontend origin to the CORS allowlist in `app/main.py` before deployment. Cross-site frontend/backend domains also need appropriate cookie configuration; the current cookies are SameSite=Lax. Prefer custom frontend/API domains on the same site.
- Configure provider OAuth callback URLs against the deployed backend. Avoid untrusted forwarded headers; configure trusted proxies for your hosting setup.
- Preserve SSE streaming: avoid proxy buffering, allow long-running requests, and use the POST streaming client in [RAG_API.md](RAG_API.md).

Fresh tables are created on startup. For older RAG schemas, run the compatibility migration as a one-off job before rollout; `create_all()` does not alter existing tables.

## Verify a deployment

1. Confirm application startup and a 200 response from `/api/v1/health`.
2. Complete registration/login through the real frontend and verify cookie authentication.
3. Upload a small text document and verify private Cloudinary storage.
4. Ask a relevant question, verify citations, and check incremental SSE delivery.
5. Confirm saved history, downloads, and deletion behavior.

Keep credentials in hosting settings. Do not commit or paste them in chat. Confirm the provider's plan, pricing, timeouts, and persistent-service configuration before creating resources.
